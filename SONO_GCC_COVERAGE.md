# Sono-GCC operation coverage

The inventory contains the 161 distinct operation names dispatched by the current `WatchVm`, including the 36 concrete easing variants. This is the repository VM inventory, not the complete Sonolus specification.

- VM dispatch operation kinds: **161**
- Direct-native operation kinds in v6: **41**
- Additional VM scalar-cut operation kinds in v6: **120**
- Current code-generation policy: **at least two direct-native operation nodes per emitted region**; singleton regions stay in WatchVm.
- Operation kinds accounted for by direct code or the scalar-cut boundary: **161 / 161**
- Runtime operations remain implemented and executed by WatchVm. The cut boundary passes their ordered `f64` results into a native parent; it is not a native-to-VM callback and does not make those operations native.
- Any graph node outside a safe native region continues through WatchVm. The scalar cut is used only when a statically bounded native parent consumes it; loops, branches, and effects are still evaluated wholly inside the VM operation.
- The Follow-up #44 singleton-region filter remains. Follow-up #45 v6 additionally routes `Lerp`, `LerpClamped`, and all easing variants through WatchVm after exact-bit differential testing found NaN-payload sensitivity in native interpolation. The 41 direct-native operation implementations are available only inside eligible regions; the coverage count is not a claim that every such graph node executes natively.
- Direct native DLL compilation/loading currently targets Windows. Other platforms retain safe VM execution.

## Watch operations supported with compatibility limitations

`WatchVm` implements the 14 stack functions, `Random`, `RandomInteger`, and
`StreamSet` under an explicitly approximate compatibility contract. The
operation inventory marks them `Approximate`, separate from both `Supported`
and `Unsupported`. Runtime use warns once per render job and can be rejected
by the strict Watch compatibility policy. The static analyzer reports their
presence as partial; static presence still does not prove that a callback
reaches or executes the operation.

These stateful operations remain excluded from direct-native Sono-GCC regions.
Callbacks containing them execute in ordered WatchVm evaluation, preserving
side-effect order. GCC may consume a VM scalar cut around other eligible
operations, but this does not make the operation itself native. Exact
official-client sequences, stack ABI edges, and mutable-stream lifecycle
remain unverified. See [the Watch semantics closure](WATCH_SEMANTICS_CLOSURE.md)
for the chosen bounded behavior and remaining parity gaps.

The v4/v5 optimization measurements and the v6 verification results are
documented in [SONO_GCC_OPTIMIZATION_REPORT.md](SONO_GCC_OPTIMIZATION_REPORT.md)
and [SONO_GCC_OPTIMIZATION_VERIFICATION.md](SONO_GCC_OPTIMIZATION_VERIFICATION.md).

Native direct-operation differential test: `cargo test --offline sono_gcc::tests::native_regions_and_vm_cuts_match_watch_vm_over_adversarial_numbers -- --nocapture` (Windows only). It compares exact result bits, evaluation/function accounting, memory, and display-list state over ordinary values, signed zeros, multiple signed NaN payloads, infinities, extremes, epsilon, and subnormals. The v6 test also asserts that `Lerp`, `LerpClamped`, and easing operations follow their declared native or VM-cut path.

Mixed-cut differential test: `runtime_cuts_preserve_order_lazy_effects_memory_and_display_state` compares a native scalar parent around VM `Set`, `Get`, `If`, `Play`, `Draw`, and `Spawn` cuts, including effect order, memory, display list, counts, and the inactive lazy branch. It is representative, not an exhaustive per-operation differential suite.

“Real-engine exercised” records operations observed in the four time-1 Watch checkpoints; names absent from those counters are explicitly marked. Counts are in the matching checkpoint logs under `artifacts/sono-gcc-follow-up-v4/`.

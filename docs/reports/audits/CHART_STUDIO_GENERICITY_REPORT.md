# Prompt #42 — Chart Studio Genericity Report

## Executive result

Chart Studio now has a defensible **generic structural LevelData editor**, a
bounded optional declarative authoring overlay, canonical undo/redo and export,
and a preview path that reaches the production Watch/runtime renderer. The
previous authoring palette/schema check incorrectly used Watch callback
archetypes as if they were declarations of LevelData entity types. This pass
corrects that boundary: LevelData archetype names come from `EnginePlayData`;
`EngineWatchData` remains runtime data.

This proves operation on the three materially different fixture packages
available in this repository, with production Watch and CPU frame rendering
for the tested engine/level/resource combinations. It does **not** prove
semantic chart authoring for arbitrary Sonolus genres or engines. No supplied
fixture was a non-rhythm-game engine, no engine-provided authoring schema is
currently consumed automatically, and the high-level editor remains
schema-dependent. Automatic gameplay-semantic inference is intentionally not
claimed.

## Genericity levels

| Level | Meaning | Result | Evidence / boundary |
|---|---|---|---|
| A — Structural | Load and edit canonical LevelData without understanding gameplay semantics | **PASS for represented canonical LevelData** | Opaque entity data, flattened unknown fields, raw JSON fallback, generic create/duplicate/delete/reorder/copy/paste, and bounded structured JSON inspection. |
| B — Round-trip | Preserve a level through production standalone export and re-import | **PASS for tested fixtures** | Deterministic gzip export is parsed back through the production loader and compared as canonical values. This is semantic JSON equality, not original-byte identity. |
| C — Runtime | Execute/preview through the normal authoritative runtime | **PASS for tested combinations; broad engine coverage unproven** | Three checked-in fixture packages pass production `WatchRuntime` and `RenderConfig::render_frame` CPU frame generation. This is not proof every engine or every edited entity set is runtime-valid. |
| D — Declarative | Give authors explicit engine-bound controls without hardcoding engine behavior | **PARTIAL / available as an optional schema overlay** | Version 1 supports identity-bound archetype labels, categories, inert templates, JSON Pointer properties, explicit timing, required/range/enum constraints. The schema is not generated from engine data and has no in-app authoring tool. |
| E — Automatic semantics | Infer gameplay meaning, relationships, lanes, notes, hit logic, or entity references for arbitrary engines | **NOT IMPLEMENTED; not claimed** | Names, JSON keys, visual behavior, and Watch graphs are not treated as sufficient evidence of authoring semantics. |

The overall claim is therefore **generic structural authoring with an
optional declarative overlay**, not a universal semantic chart editor.

## Repository and data audit

### What the engine package tells us

The Sonolus Engine Play Data specification defines `EnginePlayData` as the
resource used by levels to populate play-mode entities. Each Play Data
archetype has a `name` referenced by LevelData entities and can declare
`hasInput`, callback indexes, imports, and exports. Those declarations are
distinct from Watch callback archetypes and Watch node graphs. The current
authoring need addressed here is the exact level-facing archetype list; it is
not enough to infer arbitrary authoring semantics. See the [Sonolus Engine
Play Data specification](https://wiki.sonolus.com/engine-specs/resources/engine-play-data)
and [archetype specification](https://wiki.sonolus.com/engine-specs/resources/engine-play-data-archetype).

Before this change, Chart Studio’s archetype palette and schema validation
consulted `EngineWatchData`. That could show callback-only names and could
reject valid Play Data names. `EnginePackage` now optionally loads
`EnginePlayData` from supported package/directory member names and exposes
those names as the level archetype declaration source. Missing Play Data does
not disable raw archetype editing. Unknown fields on the parsed Play Data and
archetype records are retained as flattened JSON.

`EngineIdentity` hashes the loaded semantic tuple of metadata, configuration,
ROM, Play Data, and Watch data. It excludes filesystem location and ZIP
container bytes. A Play Data change now invalidates an authoring schema even
if Watch data did not change. Because this changes the inputs to the identity
hash, a schema carrying an identity generated by the older hash recipe must be
rebound using the current `engine-identity` command; schema version 1 itself
remains readable.

### What LevelData does not tell a generic editor

LevelData provides canonical entity archetype identifiers, entity data,
metadata, `bgmOffset`, and unknown root/entity fields. It does not, by itself,
provide a universal editor for:

- which entity is a note, lane, connector, visual object, or gameplay event;
- field labels, units, valid ranges, defaults, or cross-field constraints;
- relationships/references, stable entity identity, or safe reference repair;
- graph placement, snapping, quantization, or gameplay-specific visualization.

The optional schema can declare some authoring information explicitly, but
constraints in that file are **authoring conventions**, not assertions about
Watch/runtime requirements. The Sonolus specification’s `hasInput` property,
for example, has explicit playable-entity meaning at the Sonolus boundary; the
current Chart Studio does not use it to invent hit logic or to create
engine-specific editor behavior.

## Implementation changes

### Engine declarations and validation

- Added optional `EnginePlayData` parsing for ZIP and directory engine
  packages.
- Added `EnginePackage::level_archetype_names()`; it returns only names
  declared by Play Data and returns an empty list when Play Data is absent.
- Chart Studio’s engine palette, schema archetype validation, and the
  structural level validator now use that level-facing declaration.
- Watch archetypes remain runtime callback metadata. A Watch name is no
  longer a substitute for a Play Data declaration.
- The GUI reports when Play Data declarations are missing, keeps raw
  archetype input available, and identifies schema-free operation as
  **Generic / Raw Authoring Mode**.

### Structural editing and preservation

The source of truth remains `formats::LevelData` / `LevelEntity`; there is no
parallel chart graph or editor runtime. Raw entity JSON remains available for
all fields. The structured inspector enumerates primitive/empty-container
paths without assigning field meaning. It uses RFC 6901 escaping, supports
negative values, and falls back to raw JSON when payload size/depth exceeds
limits. Generic edits do not renumber references because the editor has no
universal entity identity/reference contract.

Unknown root, metadata, entity, and payload JSON values are preserved by the
canonical serialization model. The guarantee is value-level preservation
after parsing/serialization, not byte-for-byte retention of whitespace,
member ordering, or an input gzip container.

### Declarative authoring schema

The optional `sono-chart-authoring-schema` v1 model is external, inert JSON
bound to the engine content SHA-256 and exact Play Data archetype names. It
supports:

- human labels, categories, descriptions, and unknown-field retention;
- optional initial entity-data templates;
- JSON Pointer field descriptors and type-preserving edits;
- explicit `watchSeconds` / `mediaSeconds` timeline bindings;
- optional required, numeric-bound, and string-enum authoring constraints.

The file has no expression language, callbacks, shader/script code,
filesystem/network access, or process execution. It is validated against the
loaded engine. Invalid, stale, or mismatched schema data leaves raw authoring
available. Template and property edits use the same `ChartDocument` mutation
and undo/redo path as generic editing.

Bounds currently include a 1 MiB schema file limit, 64 KiB initial template
limit, JSON depth 32 and 8,192-node schema/template traversal, at most 4,096
archetypes and 16,384 properties, JSON Pointer depth 16 and 512 bytes, and
raw-inspector limits of 8,192 nodes, depth 64, 4,096-byte paths, and 65,536
bytes per string. Large/unsupported values remain accessible in the raw editor
when possible; bounded inspector refusal is not data deletion.

The UI exposes matching schema labels/categories and typed controls for
described existing values. Editing is committed through the existing raw-JSON
apply action. This pass did not add a schema-authoring GUI or automatically
derive a schema from Play Data imports/exports. The example file
`examples/chart-authoring-schema.json` is a template and its identity/archetype
must be replaced before use.

## Timing and semantic boundary

`bgmOffset` remains canonical LevelData state. Timing fields are engine-owned
unless a matching schema explicitly binds a JSON Pointer. The schema supports
only explicit Watch-seconds and media-seconds bindings. Media time maps to
Watch time through the established invariant:

```text
media time = Watch time + bgmOffset
```

The existing Watch runtime owns `#BPM_CHANGE`, `#TIMESCALE_CHANGE`, and
beat/time conversion. Chart Studio does not parse a second BPM system or infer
beat timing from arbitrary JSON names. Its optional beat reference grid is
editor metadata, not LevelData or Watch semantics. A schema-created entity
starts with its author-provided data; the editor does not fill guessed runtime
defaults, so a structurally valid creation can still be rejected or behave
incorrectly when an engine requires other data or valid relationships.

There is one runtime traversal: Chart Studio captures a canonical LevelData
snapshot and calls the production `RenderConfig::render_frame` route, which
uses the normal Watch runtime and renderer. There is no Chart Studio Watch
evaluator. Preview evidence is limited to the engine, level, resources, time,
backend, and configuration exercised; the test below asks for a frame at
Watch time zero.

## Compatibility analyzer

The compatibility report now gives separate assessments for:

1. the umbrella Chart Studio authoring result;
2. raw LevelData authoring;
3. the loaded LevelData canonical parse/serialize round-trip;
4. optional authoring-schema availability;
5. high-level editor availability;
6. preview execution.

This analyzer does not accept a schema input or execute a preview. Accordingly
it reports schema availability and preview execution as unknown in static
analysis, and high-level editing as partial when no matching schema was
provided. Runtime compatibility remains in the existing Watch/runtime
assessments. Its round-trip is an in-memory canonical comparison, explicitly
not a byte-identity claim or the standalone gzip export/reimport test.

looks correct.

## Adversarial and synthetic evidence

Synthetic tests use an archetype named `Mysterious` with data containing a
negative number, a string enum, and an opaque `entity:later` reference. The
tests verify that labels/constraints/templates can be declared explicitly,
range/enum/required checks behave as described, type changes are rejected,
unknown values survive edits, and undo/redo restores canonical state. These
tests do not claim that this synthetic engine can execute in Watch.

Other focused cases cover escaped JSON Pointer keys (`/` and `~`), arrays,
negative values, empty containers, invalid pointer escapes, stale engine
identities, future/unknown schema fields, old schemas with omitted optional
fields, Play Data identity changes, oversized templates, deep JSON, wide JSON,
and oversize strings. They verify bounded generic behavior and safe fallback,
not semantic validity of adversarial engines.

## `sonolus.py` investigation

The upstream project describes `sonolus.py` as a Python library for Sonolus
engine development, and the Sonolus framework list also identifies it as an
engine-development library. It is therefore a plausible **authoring-time
source** for a future explicit schema exporter: the engine author has source
knowledge unavailable in a compiled package. It is not a runtime requirement
for this renderer and was not added as a dependency or invoked by Chart Studio.
This pass did not establish a supported stable API for exporting the exact
schema format defined here, so no compatibility claim or integration is made.
See [sonolus.py upstream](https://github.com/qwewqa/sonolus.py) and the
[Sonolus frameworks list](https://wiki.sonolus.com/engine-specs/frameworks-and-tools).

## Remaining limitations and next evidence needed

To strengthen the generality claim without hardcoding engine behavior:

1. Add a licensed, redistributable non-rhythm Sonolus engine fixture and a
   matching standalone LevelData/resource fixture; run structural export,
   Watch, and normal render tests.
2. Have engine authors provide an explicit schema sidecar or a documented
   authoring metadata export (potentially generated from their source toolchain
   such as `sonolus.py`). Keep that schema external and content-bound.
3. Exercise schema loading and edit/undo/redo manually in the packaged GUI,
   then save/reopen/export and visually inspect an actual preview image.
4. Add engine-specific semantic validation only as explicitly authored
   contracts or through the engine’s own Watch runtime. Do not infer meaning
   from labels, names, or visual effects.
5. Measure UI responsiveness on larger LevelData files before making a
   performance claim.

Until those gaps are addressed, the accurate user-facing promise is: **Chart
Studio can structurally edit and round-trip supported Sonolus LevelData, use
optional explicit schema hints for declared fields, and preview tested
engine/level combinations through the normal renderer. It is not a universal
engine-specific charting interface.**
